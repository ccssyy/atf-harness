# ATF-Harness Owner 分析——项目态势与训练 Agent 架构方案

**日期**：2026-09-14
**性质**：owner 侧综合分析（整合 R2 门 2 产出、内核侧三议题、agent-loop 门 1 讨论稿；**不产生代码、不改既有决议**）
**输入基线**：内核 `v0.6.0b0`（`b6db349`）｜harness `main` @ `2669d8c`（R2 门 2 本地未推）｜pin `v0.6.0b0`｜契约 v2
**结论先行**：**接口层已经真实、驱动源仍是桩、宿主通道还没有。** 训练 Agent 现在具备"真实内核 + 真方法面 + 假大脑 + 无人应答"的形态；把它变成可用的 Agent，缺的不是更多方法，而是三件**非方法面**的事：**一个真实 provider（+ adapter）**、**一个带终止判据与预算的 loop**、**一条人工应答通道**。其中**最紧急的不是这三件，而是一个治理隐患**（§4.1）。

## 2. 内核侧三议题：它们真正约束的是 loop 的设计前提

| 议题 | 实质 | 对 harness/loop 的约束 |
|---|---|---|
| ① 审批事实承载（**根因**） | 架构写「外部 fact root, append-only」，实现是进程内 dict（无落盘/无重载） | **loop 依赖的一切状态必须落本侧事件流**——"再查一次内核"会得到"不存在"而非"未推进"，语义不同必误判 |
| ② 会话级预录入口 | 契约预留 `ledger_record`（setup 基建），内核未实现；只解决同进程预录 | 问答轨（应答即授权凭据）是当前唯一可行的运行时授权路径 → **双轨必须并存** |
| ③ 完整性 Gate advance 入参 | 签名简单，但合成 refs 不构成真实证据链 | 不阻塞；将来真实链路批次再覆盖 |

**结论**：三议题都不阻塞当前工作，但它们把 loop 的恢复路径钉死为**单向依赖本侧 append-only 事件流**。这条公理（讨论稿 §2.3）应当写进 loop 设计，且**措辞必须准确**（见 §4.2）。

## 3. agent-loop 讨论稿：我接受什么、我强化什么

### 3.1 接受（五项 schema 级决策的推荐口径）

| # | 决策 | 推荐 | 我为什么同意 |
|---|---|---|---|
| A1 | 是否引入 step 粒度事件 | **不新增**；`turn/end.payload` 补 `step_count`/`decision_count`（纯增量不 bump） | `tool/call`↔`tool/result` 配对已是可恢复边界；12 类语义尚未在真实负载下检验，不宜扩容 |
| A2 | 终止判据 | **裁剪版四重判据 + 显式轮次预算**（`max_steps_per_turn` 32 / `max_turns` 8）；`stopReason` 扩面；**不新增退出码** | 真实模型下"无预算的 loop 会失控"，这是 Faux 期不存在的风险；预算耗尽复用 exit 1 是对的（它不是治理事件） |
| A3 | 工具批次 | **显式拒绝并行**；一次决策一个工具；adapter 负责展开 | 三条治理理由都成立：审批是逐工具一次性消费（并发＝批量授权，破"无配额复用"）、事件顺序须等于决策顺序、恢复可确定性 |
| A4 | 审批与 turn | **维持现状**（嵌在 turn 内、挂起收口 turn、resume 开新 turn）+ 固化 INV-1/2/3 | 与 R2 正在跑的实现零冲突；跨进程"续同一 turn"不可自证 |
| A5 | 第 13 类事件 | **本切片不新增**；保留位承接 | 需求时点都在后续切片；保留位机制是当时预留的正确出口 |

### 3.2 强化：类型拆分不是"可选的独立工作包"，而是**治理前置**

讨论稿 §6 指出：`src/llm/provider.ts` 里 `export type LlmDecision = ScenarioStep`，而 `ScenarioStep` 含 `promote` —— runner 收到它**直接调 `promoteArtifact`（晋升闸 A）**。Faux 脚本由测试编写，无风险；**但切片 3 一接真实模型，模型只要能产出 `promote` 决策就绕过了 4 工具面直触晋升闸**，与 TCB 铁律 + "工具面收敛为 4"正面冲突。

**我的判定**：这是全项目当前**唯一的高严重度隐患**，且它是**时间敏感**的——它的危害随"真实 provider 落地"的那一刻激活。因此：

1. 类型拆分 + `assertModelDecision` 守卫（provider 返回脚本指令 → fail-closed）应作为**切片 0 立即启动**，与 R2 门 2 的推送/验收不冲突（R2 未改 `runner.ts`，两者文件面不重叠）；
2. 验收标准：`tsc` 类型检查 + 守卫正反例 + 既有测试零回归；
3. 它**不依赖** A 组任何结论——这是把它单列的全部理由，也是它最便宜的时候。

### 3.3 补充：一处语义边界必须写清（防"两个真相源"）

讨论稿 B2 提议：把"某闸门推进过"写成 harness 侧事实。方向对，但**语义必须限定**：harness 事件流里写的是「**我方请求并收到某某响应**」这一**客户端观察事实**，**不是**内核侧状态的权威副本。否则内核将来落实持久化（议题①路线 A）时，会出现"harness 说推进过、内核账本里没有"的两真相源冲突。措辞建议：`gate/advance-ack`（观察）而非 `gate/advanced`（状态断言）。

### 3.4 补充：一个更早可达的产品台阶（L1a）

按现有切片顺序，真实 provider 与"人在回路"都在切片 3（= Phase 3 首切片）。但这两件事其实是**两种能力**，可以分开上：

| 台阶 | 内容 | 用户能做什么 | 依赖 |
|---|---|---|---|
| **L1a** | 真实 provider + loop（切片 0/1/2 完成）+ **一条最小人工应答通道**（CLI 或本地 socket，把 `approval/request` 转达给你、把你的答复回写为 `approval/response`） | 让模型**自主跑只读动作**（看状态、扫事实、查闸门）；遇到高危写动作自动 `suspended(75)` 等你放行 | 切片 0–2 + 一条最小通道（**不必等 ACP 全量**） |
| **L1** | ACP 宿主嵌入 + 审批人在回路（ADR-09 消费面） | 在宿主里连续对话 + 逐项审批 + 看过程 | 切片 3（含 owner 对真实 provider 的授权） |
| **L2** | 真实 run / 真实数据 + 内核议题① 落地 | 作用于真实训练链路 | R2 之后的真实 run 夹具 + 内核承载议题 + owner 对真实 effect 的授权 |

**建议**：把 L1a 作为**"可试用里程碑"**（你问过"什么时候能试用"——它比 L1 早，且验证的正是"loop + 真实模型 + 人在闸口"这条主干）。

## 4. 训练 Agent 的架构方案（除方法面之外的全貌）

### 4.1 三层 + 一条耦合面

| 层 | 职责 | 现在的载体 |
|---|---|---|
| **L1 内核（业务真相）** | 五业务模块、G 闸门、四事实 owner、run journal | ATF 仓（只读对端） |
| **接口层（唯一耦合面）** | 会话协议（通道）+ 7 方法（能力面）+ canonical output | 契约 v2 + 内核 `serve`；**已真实** |
| **L2–L4 harness（过程管控）** | ① loop（驱动/终止/预算）② 守卫管道（schema → 审批双轨 → 桥接 → canonical 校验）③ 工作区三层（T0/T1/T2 + 闸 A/B）④ append-only 会话日志（**唯一跨进程凭证**） | harness 仓；①②尚待切片 0–2 |
| **驱动源（大脑）** | provider 接口 + adapter（投影↔模型消息、多工具展开、错误回填） | Faux（桩）→ 切片 3 换真实 |
| **宿主（人在回路）** | 转达审批请求、回写应答、订阅过程事件 | 缺 → L1a 最小通道 → L1 ACP |

### 4.2 四条不变量（loop 设计的公理层）

| # | 不变量 | 来源 |
|---|---|---|
| **INV-A 状态只落本侧** | loop 依赖的一切状态必须在 harness append-only 事件流有留痕；禁止以"再查内核"为恢复依据 | 内核议题① + R2 决议 §3.3 |
| **INV-B 一次决策一个工具** | 拒绝并行批次；多工具响应由 adapter 展开为顺序决策 | 讨论稿 A3（审批一次性消费 / 顺序确定） |
| **INV-C turn 不跨进程** | 一 turn = 一次同进程连续执行；任意终局收口 turn；resume 开新 turn | 讨论稿 A4（INV-1/2/3） |
| **INV-D 模型面不含脚本指令** | `LlmDecision` 只含 `tool_call` / `message` / `final_answer`；其余为测试基建，运行时守卫拒绝 | §3.2（TCB 铁律） |

### 4.3 loop 的五件套（实现清单）

1. **驱动源**：`LlmProvider.decide(context)` 真正消费 context（现状被忽略）；
2. **终止判据 + 预算**：四重判据 + `max_steps_per_turn` / `max_turns`，预算耗尽 → `failed(budget_exhausted)`，模型不可见；
3. **守卫管道**：参数 schema → 审批（账本轨优先，未命中走问答轨）→ 桥接执行 → canonical 校验；
4. **回填**：`tool/result` 落盘（携 `call_ref`）→ 回到组装 context（闭环）；
5. **留痕**：审批结论由 `resolveCredentialState` 纯函数推导；闸门推进以**观察事实**记（§3.3 措辞）。

## 5. 路线图与关键路径

```text
[R2 门 2 完成] ── 真实内核 + 真方法面 + Faux 驱动 + 无人应答   ← 当前
      │
      ├─► 切片 0  类型拆分 + assertModelDecision 守卫         （治理前置，立即可做）
      ├─► 切片 1  loop 骨架：终止判据 + 预算 + step 元数据      （依赖门 1 通过 + R2 报告）
      ├─► 切片 2  adapter 契约 + 多工具展开 + 错误回填 + 公理兑现
      ├─► L1a     真实 provider + 最小人工应答通道             ← 可试用里程碑
      ├─► L1      ACP 宿主嵌入 + 审批人在回路（Phase 3 首切片）
      └─► L2      真实 run/数据 + 内核议题① + owner 授权真实 effect
```

**关键路径判断**：**切片 0 → 1 → 2 → L1a** 是主干；L1/L2 分别卡在"宿主实现"与"内核承载 + 真实数据授权"两处外部依赖上。R2 之后的下一件大事**不是**继续扩方法面，而是**把 loop 与真实 provider 接上**。
