# ATF-Harness P2-S2 审批应答语义设计草案——非批准类应答的处置

**日期**：2026-09-10
**性质**：设计草案（回应 owner 提问，讨论稿）
**范围**：P2-S2 交互问答审批轨的应答分类、分支处置与语义不变量
**前置依赖**：D1（ACP 消费面设计定型）——本草案的 schema 结论需与 D1 一并拍板
**关联**：ADR-07（双轨审批）需增补；ADR-06 会话事件 schema 需扩展

---

## 0. 结论先行

1. **现状**：Phase 2 规划对问答轨只定义了主干——「对端回 allow 则执行，deny 或超时则 block」。**对「拒绝后的继续/终止分级」「提问追问」「修改意见」三类情况没有设计**，属真实缺口，需在 P2-S2 开工前补齐。
2. **核心判断**：应答不是二元的。建议定义 **六类应答**（allow / advise / deny / abort / ask_back / timeout），六条处置路径，其中两条关键设计不变量为：
   - **审批对象确定性**：审批的对象永远是「具体某一次调用（工具名 + 参数）」，用户的修改意见不自动改写参数并执行，而是回填模型由其重新提案；
   - **超时 ≠ 拒绝**：无应答是「待恢复」态（挂起），不是否决态。
3. **schema 影响**：问答轨不是「一问一答」，需要「审批会话」模型（`approval_session_id` 配对多轮往返 + 与 `tool_call_id` 的引用链）。**该结论与 D1 消费面定型强耦合，建议合并拍板**，否则 Phase 3 接宿主时会改会话 schema。

## 1. 问题陈述

owner 提出的三类情况，对应三个设计空白：

| 情况 | 现状规划覆盖 | 缺口本质 |
|---|---|---|
| 用户拒绝 | 有「deny → block」一条 | 未区分「这一步不做、模型可换路径」与「整个任务终止」；未处理反复重提 |
| 用户提出疑问 | 无 | 未定义「非决策类应答」；未定义多轮往返与配对语义 |
| 用户给修改意见 | 无 | 未定义意见如何回流；存在「授权对象被偷换」的审计风险 |

## 2. 应答分类与处置矩阵

| 应答 | 语义 | 落盘事件 | 处置 | 回流去向 |
|---|---|---|---|---|
| **allow** | 批准本次具体调用 | `approval/granted` | 执行该次调用，结果回填模型 | 继续下一步 |
| **advise** | 提出修改意见，未批准也未否决 | `approval/advised`（意见原文必留） | 意见作为反馈回填模型，**由模型重新提案**；不自动改写参数执行 | 回到提案（形成新一次 request，引用前次提案） |
| **deny** | 拒绝本次调用 | `approval/denied`（拒绝理由建议留） | 该调用不执行，返回结构化 block（`reason: approval_denied`）；模型可换路径继续 | 继续（换路径）；同提案重试计数 +1 |
| **abort** | 终止整个任务 | `approval/aborted` | run 进入终态，按既定退出码结束，不重试不降级 | 结束 |
| **ask_back** | 提问 / 要求补充信息 | `approval/clarification` | 补足上下文后重发 request，**配对到同一审批会话** | 再问一次（多轮往返） |
| **timeout / 无应答** | 无人应答（缺省或超时） | `approval/timeout` | run 挂起（suspend），保留待决状态；**不等同于拒绝** | resume 后重新进入等待 |

设计要点补充：

- **advise 的提案演化链**：模型据意见重新提案时，新 request 需带 `supersedes`（引用被建议/被拒的前次提案），使审计可回答「最终执行的这一次，是基于哪条意见改出来的」。
- **「授权即改」快捷路径**（可选，建议 v1 不做）：允许应答方直接给出修正后的参数并同时批准。它省一次往返，但会让「批准的对象」与「实际执行的对象」分离。若日后要做，建议在 `approval/response` 中显式增加 `amended_proposal` 字段并在审计视图中高亮。**待 owner 取舍**（子决策 E）。
- **拒绝循环防护**：同一提案（工具名 + 参数摘要）被拒后不得立即原样重提；计数达阈值（建议 2 次）→ 升级为 abort 或上报。阈值取常量，不暴露给模型。
- **应答者身份**：每条应答必须落 `actor`（Phase 2 为桩对端标识，Phase 3 为宿主/人）——「谁批的」是审计必需项，不能只有「批了」。

## 3. 流程

```text
提案（工具名 + 参数 + 调用理由）
  │
  ├─ 落 approval/request（approval_session_id ↔ tool_call_id）
  │
  └─ 等待应答 ─┬─ allow      → approval/granted   → 执行 → tool/result → 继续
               ├─ advise     → approval/advised   → 回填模型 → 重新提案 → 回到顶部
               ├─ deny       → approval/denied    → block 回填 → 换路径（重试计数 +1，超阈值升级）
               ├─ abort      → approval/aborted   → run 终态（既定退出码）
               ├─ ask_back   → clarification      → 补上下文 → 重发 request（同一会话）
               └─ timeout    → approval/timeout   → 挂起 → resume 后重新等待
```

---

## 4. 语义不变量（设计红线）

1. **审批对象确定性**：一次审批只覆盖一个确定的具体调用；参数变更即视为新提案，必须重新审批。
2. **无配额复用**：问答轨的一次 allow 不产生可复用授权（区别于账本轨的配额语义），下一步仍需独立审批（或由策略层显式授予）。
3. **超时非否决**：挂起态与拒绝态在事件类型、退出码、可恢复性上完全区分。
4. **可审计配对**：每次应答都能回溯到被应答的那次请求、被审批的那次调用、以及它替代的前次提案。
5. **与账本轨互不污染**：账本轨语义（一次性消费、exit 78 锚点）零改动；两轨在同一 run 中并存时，优先级与冲突规则需在 D1 中定（子决策 F）。

## 5. 对会话 schema 的影响（待 D1 合并拍板）

- 事件类型：由原计划的 2 类（`approval/request`、`approval/response`）细化为 1 + 6 类（请求 + granted / advised / denied / aborted / clarification / timeout）；或保留统一 `approval/response` + `verdict` 枚举——**两种建模方式需择一**（子决策 C）。
- 新增关联字段：`approval_session_id`（多轮往返配对）、`tool_call_id`（审批对象引用）、`supersedes`（提案演化链）、`actor`（应答者身份）。
- schema 版本：由 schema v0 → v1 显式 bump，与本 slice 的扩展一并声明。
