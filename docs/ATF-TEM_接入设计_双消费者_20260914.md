# ATF ↔ TEM 接入设计（双消费者：内核 KB 适配 ＋ harness 两道闸）

> **权威副本**：训练经验 Memory 仓（本文件）｜另投 harness `docs/` 与 内核 `_docs/` 供执行方阅读（三处同期一致，冲突以本处为准）
> **阶段**：**接口级设计**（不含实现；对象模型 / 检索算法 / 存储归 TEM 侧）
> **日期**：2026-09-14 ｜ **签发**：owner
> **依据**：《记忆分层口径确认与 Phase 3 前置登记》（2026-09-11）＋《R2 门 1 评审·门 2 放行》§2.3/§3.3/§5 ＋ 内核 `docs/architecture/experience-kb-contract.md` ＋ TEM v1–v9 与 10 条已定决策
> **结论先行**：TEM 是**经验的唯一权威存储与对象模型所有者**；**两个消费者**——A＝内核 skill 面（经 KB 适配层，服务"脱离 harness 单独使用内核"的场景）、B＝harness loop（写闸回灌 ＋ 读闸注入）。本设计只定**接口与两道闸**。

## 0. 三条纪律（否则会长出两套经验）

| # | 纪律 | 落地要求 |
|---|---|---|
| ① | **单一对象模型** | 对象模型与检索语义**只由 TEM 定义**；内核 KB 与 harness 注入条目都只是**投影/调用**，不得各自演化字段 |
| ② | **同 run 单一写入者** | 谁执行该 run 谁回灌（harness 驱动的 run → harness 写；内核 skill 独立跑的 run → 内核侧写）；TEM 侧以 **run 引用**去重 |
| ③ | **KB 是投影不是并行真相源** | TEM 接入后二选一：KB 由 TEM 派生并标只读，或保留本地写入但**声明"待同步"** |

## 2. 双消费者接口面

| | **消费者 A：内核 skill 面** | **消费者 B：harness loop** |
|---|---|---|
| 谁在用 | 不用 harness 的用户（skill / CLI 直接跑训练流程） | Agent 驱动的 run |
| **读** | 训练前先验（阈值锚 / 构造默认）→ **目标：来自 TEM 建议卡** | context 组装时检索注入（Claim → 追溯 Case） |
| **写** | run 后经验（判定记录等）→ **目标：提炼为 EvidenceEvent 提交 TEM** | run 收尾回灌 EvidenceEvent |

| 目标形态 | **KB 降级为 TEM 的本地投影 / 适配层**（保离线可用与确认链） | 两个闸 ＋ 注入点（切片 2 落位） |

## 3. 两道闸（harness 侧，本节即切片 2 的"注入口三条"）

### 3.1 写闸（提炼）：harness → TEM

- **原料只取事实层**：会话日志（append-only）＋ T1/T2 产物 ＋ `domain_refs`；**不得取压缩后的上下文视图**（硬约束 #1，防 compaction 失真污染记忆）；
- **裁决者 = 人工审批**（v1 不做自动提炼）；
- **产出 EvidenceEvent 最小字段**：`run_ref`（`{journal_type, fact_id, sha256_digest}` 三元组）／`task_profile_ref`／`intervention_refs`（决策与审批摘要的引用）／`outcome`（结果与成本）／`state`／**环境指纹**（模型 / 内核 pin / 数据规模）＋ `valid_until`；
- **失败语义**：写入失败 → 记事件 ＋ 待重试；**不阻塞 run 收尾**。

### 3.2 读闸（注入）：TEM → harness

- **时机**：context 组装时**一次**检索（不逐 turn 检索）；带 task-profile；
- **裁决**：相关性阈值 ＋ **注入配额**；
- **注入条目**：必须带**来源引用**（可追溯到 Case/Claim id）；**可被 compaction 折叠，但引用链不得被吃掉**；唯一例外 `structural_preconditions`（结构前提）类**不折叠**；
- **失败语义**：检索失败 → 记事件 ＋ **无记忆运行**（记忆是增强而非依赖）。

### 3.3 注入点位置

落在**切片 2 定义的 context 组装**处：`transformContext` 投影之后、`provider.decide()` 之前，作为**可压缩注入条目**参与投影。不得另起注入通道。

## 4. 内核侧 KB 适配（消费者 A）

### 4.1 字段对齐（KB → TEM 语义）

| KB 字段 | TEM 对应 | 说明 |
|---|---|---|
| `signal_calibration` | **先验锚**（Claim 的 recommended_params 一类） | TEM 接入后由建议卡派生；KB 保留为本地缓存 |
| `construction_defaults` | **干预默认值**（Claim 的 intervention 侧） | 同上 |
| `provenance.source_refs` | **run / 会话引用** → `run_ref` 三元组 | 引用字段语义向 EvidenceEvent 对齐（KB 契约已预留） |
| `provenance.append_chain`（`prev_sha256`/`confirmed_by`） | **审计链** | 保留：对应"提炼闸＝人工审批"的落地证据 |
| `judgment_records` / `guardrail_methods` / `weak_field_instances`（documentation-only） | **Case 素材** | 契约明令"不得为其建立产品消费机制"→ 只作素材，不做机械搬运 |

### 4.2 演进三步（不淘汰 KB）

1. **只读投影**：KB 由 TEM 派生（＋离线缓存），本地追加冻结；
2. **本地追加但标"待同步"**：允许离线写入，`provenance` 注明未同步（需 TEM 侧接受"待同步"态）；
3. **双向同步**（若确有必要）：仅在①②证明不可行时评估。

**离线降级**：TEM 不可达 → 用本地缓存 ＋ **显式降级标记**（fail-closed 不静默）。KB 的 `--confirm` ＋ sha 链纪律**全程保留**。

## 5. 接口形态与四项接口级决策（推荐值，待 TEM 侧确认）

| # | 决策 | 推荐 |
|---|---|---|
| 1 | 调用形态 | **HTTP/JSON API**（TEM 侧服务）＋ 两侧用**内置能力**调用（harness 用 Node 内置 `fetch`，符合 R2a；内核用标准库 `urllib`），**不引入依赖** |
| 2 | 调用时机 | 写＝run 收尾后一次；读＝context 组装时一次（内核侧：训练前一次） |
| 3 | 身份与隔离 | 强制**环境指纹**（模型 / 内核 pin / 数据规模）＋ `valid_until`；按项目 / 数据集作用域隔离 |
| 4 | 失败语义 | **不阻塞**（§3.1 / §3.2 已分别定义） |

**去重键**：`run_ref` 三元组（纪律 ② 的技术落地）。

## 6. 与既有决议的一致性检查

| 既有决议 | 本设计是否一致 |
|---|---|
| 记忆分层口径（三类 / 五层 / 两闸 / 四硬约束） | ✅ 一致：本文是其在"跨系统接入面"上的展开 |
| R2 决议 §2.3（durability 公理：状态必须落本侧事件流） | ✅ 注入与回灌的留痕都落在 harness 会话日志；不依赖内核内存态 |
| N1（闸门推进留痕 = 客户端观察事实） | ✅ 回灌条目同样只声明"我方观察到的结果" |
| **TEM 决策 #10**（经验状态转换由 ATF 侧 Decision Ledger 记录） | ⚠ **暂缓**：Decision Ledger 同为内存 owner（受内核议题① 约束）且内核**未暴露写入面**（7 方法无写账本/写决策方法）→ 短期先记 **harness 侧事件流**（N1 口径）；作为内核议题延伸登记 |
| R2a（零运行时依赖） | ✅ 两侧均用内置能力调用 |

## 8. 待定与风险

| # | 事项 | 说明 |
|---|---|---|
| 1 | TEM 接口未定义 | TEM 有对象模型、无 API → §5 四项需 TEM 侧确认后冻结 |
| 2 | 去重失效风险 | 纪律 ② 需 TEM 侧以 `run_ref` 支持去重，否则同 run 重复证据 |
| 3 | 迁移期"双权威" | 纪律 ③ 的落地窗口期须有明确标记，否则审计无法判断哪份为准 |
| 4 | 内核议题① 的间接影响 | 仅影响"经验状态回写内核 Decision Ledger"（决策 #10），不影响记忆闭环本身 |
