## 0. 结论先行

1. **Phase 2 定位**：能力扩展阶段——在已验证的 headless 冒烟骨架上，补齐「长会话处理能力（compaction/fsync）＋ 模型适配面（多 provider）＋ 审批第二轨（交互问答）＋ T2 冻结区治理（晋升闸 B）」四类能力。全部落点在 Phase 1 已预留的占位上（`transformContext`、`LlmProvider`、S3 审批位、S4 contracts 层），**无架构级新决策**，属于定向填充。
2. **建议范围分三档**：
   - **A 档（建议必做）**：P2-S1 compaction＋fsync、P2-S3 多 provider——二者是 Phase 3 宿主嵌入的显式前置；
   - **B 档（建议纳入）**：P2-S2 交互问答轨（ADR-07 第二轨）、D1 ACP 消费面设计定型（仅设计文档）；
   - **C 档（随消费面/外部依赖立项）**：P2-S4 晋升闸 B、C1 真实对端接入（re-pin，待内核 JSONL 会话能力发版）。
3. **建议切片顺序**：D1（消费面定型，轻量）→ S1 → S2 → S3 → S4（C 档条件触发）。每 slice 沿用 Phase 1 纪律：代码＋vitest＋冒烟命令＋PR→owner review，测试基线 109/2 不得回归。
4. **不变式延续**：零 npm 运行时依赖、内核仓只读（pin `v0.2.0b7` 不动，re-pin 需专项指令）、无 GPU、无真实 Provider、`bridge.contract.yaml` 契约流程照旧。

## 3. 各切片设计要点（规划粒度）

### D1｜ACP 消费面设计定型（仅文档，产出 ADR-09 候选）

- **目的**：在写任何第二轨代码前，先定「外部宿主（如 ACP 编排方）如何消费 harness」：dispatch/resume 的调用形态、会话透出的事件投影、审批请求如何经宿主转达人、多 provider 配置由宿主注入还是 harness 自管。
- **产出**：一份消费面定型文档（建议 ADR-09），含接口草案与事件投影白名单；不实现。
- **验收**：文档经 owner review 通过；S2/S3 任务书条款能逐条引用其结论。

### P2-S1｜会话能力升级：compaction ＋ fsync（`src/session/`）

- **compaction 设计要求（草案）**：
  1. `transformContext()` 从拼接占位升级为真实实现：超过阈值（事件数/估算 token 双指标，常量定义）触发压缩——旧事件折叠为摘要事件（新事件类型，schema v0 → v1 显式 bump），`assistant/attempt` 与被压缩事件的原始序列保留在磁盘（append-only 不删改，压缩只影响投影视图）。
  2. **领域事实白名单**：`domain_refs` 命中的事件及其相邻因果链**永不压缩**（承证事实必须留在上下文）；白名单逻辑纯函数化、可独立测试。
  3. 压缩过程本身作为 `session/compaction` 事件落盘，可审计、可重建。
- **fsync 策略（草案）**：定死 durability 契约——默认每次 append 后 `fsync`（Phase 1「先落盘再继续」语义的显式化）；提供批量模式（N 条或 T 毫秒窗口）作为性能档位，配置项收在常量层不暴露给模型。两种模式均有崩溃恢复测试（写入中途 kill 进程 → replay 不丢已确认事件）。
- **验收（草案）**：压缩触发/白名单豁免/压缩事件可重建三组正反例；fsync 双模式崩溃恢复用例；replay 与 Phase 1 既有 109 用例零回归。

### P2-S2｜交互问答审批轨（`src/tools/` ＋ `src/run/`）

- **设计要求（草案）**：
  1. ADR-07 第二轨落地：审批请求不再仅依赖账本预录，可暂停执行、向「问答对端」（Phase 2 为测试 stub 对端，Phase 3 起为 ACP 宿主）发出结构化提问，收到应答后继续。
  2. 会话事件 schema 扩展：新增 `approval/request`、`approval/response` 两类事件（D1 结论定字段），问答往返全程落盘可审计。
  3. **双轨并存不互斥**：账本轨保持 Phase 1 语义原样（一次性消费、exit 78 锚点不动）；问答轨为增量。headless 模式下问答对端缺省 = 无应答 → block，行为与 Phase 1 兼容。
  4. 超时语义显式化：应答等待超时 → 结构化 block（非 crash），退出码走既有 `resolveHeadlessExitCode()` 单出口。
  5. **应答语义（专项议题）**：非批准类应答（拒绝分级 / 提问追问 / 修改意见）的处置未含在本条四项中，已单独立稿《ATF-Harness_P2S2审批应答语义设计草案_20260910.md》（六类应答 + 六条分支处置 + 五项语义不变量 + 六个待决子决策）。其会话 schema 结论与 D1 消费面强耦合，**建议与 D1 合并拍板**后再撰写 P2-S2 任务书。
- **验收（草案）**：问答轨正例（stub 应答 → 放行）；超时反例（无应答 → block）；双轨并存回归（账本轨全部既有用例不变）。

### P2-S3｜多 provider 与热切换（`src/llm/`）

- **设计要求（草案）**：
  1. `LlmProvider` 第二实现（建议仍是脚本化 Faux 变体，**不引入真实网络 Provider**——真实 Provider 留给 Phase 5/真实验证阶段，且需 owner 显式授权）。
  2. 热切换语义：会话中途切换 provider 的合法性规则（切换点必须是 turn 边界；切换前后 `domain_refs` digest 校验连续）+ 切换事件落盘。
  3. **R2b 升级评估**：产出结论文档——Phase 0 拍板的 R2a（零外部依赖）在多 provider 需求下是否维持；若引入 SDK 依赖需 owner 显式豁免 R2a 约束。
- **验收（草案）**：同会话两 provider 交替完成的冒烟分支；turn 边界外切换被拒的反例；R2b 结论经 owner 确认。

### P2-S4｜晋升闸 B（`src/workspace/`）——C 档，随消费面需求立项

- **设计要求（草案）**：T2 冻结区（contracts）写入通道：变更 = 决策记录（who/when/why/前置契约版本）＋ 审批（双轨之一，依 S2 结论）＋ 原子变更（写入失败不留半态）；T2 内容变更触发 `bridge.contract.yaml` 一致性检查。
- **立项触发条件**：出现真实消费需求（如 D1 结论要求 harness 侧管理 T2、或内核侧契约演化需要冻结区配合）。无需求则顺延 Phase 3，不硬做。

### C1｜真实对端接入（re-pin）——条件项

- **触发条件**：ATF 内核 stdio JSONL 会话能力发版落 tag（owner 主线事项，任务书已备好）→ owner 签发 re-pin 专项指令。
- **动作**：`bridge.contract.yaml` bump `atf_upstream` → 2 个 skipped 契约用例启用 → mock 对端逐项替换为真实内核对端 → 契约测试全绿。
- **边界**：re-pin 属 Phase 2 待决清单第 6 项，但其依赖在 owner 主线，**不阻塞 S1–S3 开发**（mock 口径继续有效，Phase 1 已验证此口径可行）。

## 附录 A｜三项易抽象能力的具体形态（备任务书引用）

### A.1 fsync：落盘语义的强度

| 项 | 内容 |
|---|---|
| 是什么 | 一次系统调用：把仍在 OS 页缓存、尚未写入磁盘的数据强制刷盘，刷完才返回 |
| 现状缺口 | Phase 1 的承诺是「写操作先落盘再继续」，但 `write()` 成功 ≠ 已在磁盘。进程崩溃无碍（数据由 OS 保管），整机断电/内核崩溃则丢失未刷盘部分 |
| 具体后果 | 会话 log 第 12 条 `tool/result` 已返回成功，随后断电 → 磁盘只有 11 条 → replay 时该次 G2 判定缺证据，证据链断，不可复现 |
| Phase 2 动作 | 在 `src/session/` 写入路径上显式定死 durability 契约：默认逐条 fsync（已确认事件永不丢），批量窗口档位作性能配置；补崩溃恢复测试（写入中途 kill 进程 → replay 校验已确认事件无缺失） |
| 验收形态 | 双模式崩溃恢复用例 + 既有 109 用例零回归 |

### A.2 交互问答审批轨：审批的决策时点

| 项 | 账本轨（Phase 1 已有） | 问答轨（Phase 2 新增） |
|---|---|---|
| 授权时机 | 事前：跑之前把审批单预录进 ledger（工具名 + 参数 + 配额） | 事中：agent 真正发起调用时才提问 |
| 运行时行为 | 查账本 → 命中且未消费则执行并核销；未命中则不执行，`block(approval_missing)`，退出码 78 | 暂停执行 → 发出 `approval/request`（工具名、参数、调用理由、影响范围）→ 对端回 allow/deny/无应答 → allow 执行，其余 block |
| 是否有人在回路 | 无。模型全程不得中途问人 | 有。可逐步获取授权 |
| 留痕 | ledger 记录消费状态 | `approval/request` + `approval/response` 两类会话事件，可回放审计 |
| 兼容约束 | 语义不动（一次性消费、78 锚点） | 增量；headless 下对端缺省 = 无应答 → 行为与 Phase 1 一致 |

定位说明：本切片只做「发问—等待—按答复继续」的能力与桩对端验证，把提问转达给人的界面属 Phase 3（ACP 宿主）职责。决策时点是账本轨与问答轨的真正分野，也是宿主嵌入的必要前提。

### A.3 晋升闸 B：变更规则的唯一合法通道

| 项 | 闸 A（已实现） | 闸 B（Phase 2，C 档） |
|---|---|---|
| 管控对象 | 数据与产物（T0 → T1） | 规则与合同（→ T2 冻结合同区：领域合同、G 闸门定义、字段规格） |
