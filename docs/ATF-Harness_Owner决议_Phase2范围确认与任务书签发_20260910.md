## 1. 逐条确认口径

### 1.1 决策一 范围取舍

- **纳入本轮**：D1、P2-S1、P2-S2、P2-S3。理由：四项均可在当前 mock 对端口径下验证，且为 Phase 3 宿主嵌入的显式前置。
- **不入本轮**：P2-S4 晋升闸 B（冒烟口径下无法验证，硬做会退化为空转流程）、C1 re-pin（依赖内核侧发版，harness 侧无法推进）。二者转入条件项登记，触发条件见任务书 §5。

### 1.2 决策二 ACP 消费面定位

- D1 只产出消费面定型文档，**不实现 server、不改代码**；ACP server 本体仍在 Phase 3。
- D1 必须吸收《P2S2 审批应答语义设计草案》§5 的 schema 结论，并在文档中明确声明与 Phase 3 的边界。

### 1.3 决策三 切片顺序

- 单线推进：D1（文档）→ owner review → P2-S1 → P2-S2 → P2-S3，每 slice 交 review 后才进下一个；不接受并行以压缩周期。

### 1.4 决策四 fsync 默认档位

- 默认逐条 fsync：已确认事件永不丢，作为产品可信度底线。
- 批量窗口（N 条 / T 毫秒）保留为配置位，收在常量层，不暴露给模型。
- 两档均需崩溃恢复测试。

### 1.5 决策五 R2b 处置时点

- 在 P2-S3 内完成 R2b 评估并出结论文档，交 owner 确认后方可变更依赖策略。
- **未获 owner 确认前，`dependencies` 必须保持为空。**

### 1.6 决策六 问答轨应答语义（子决策 A–F）

| 子决策 | 正式口径 |
|---|---|
| A 应答分类粒度 | 六类：`allow` / `advise` / `deny` / `abort` / `ask_back` / `timeout` |
| B 拒绝后默认处置 | 默认「换路径继续」；终止必须显式 `abort` |
| C 事件建模 | 统一 `approval/response` + `verdict` 枚举（事件类型集合收敛） |
| D 拒绝循环阈值 | 同一提案（工具名＋参数摘要）重提 2 次即升级（abort 或上报）；阈值取常量 |
| E 「授权即改」快捷路径 | v1 不实现，仅在 `approval/response` 留 `amended_proposal` 扩展位 |
| F 双轨并存规则 | 账本轨优先：先查账本，未命中再走问答轨；账本轨语义零改动 |

五项语义不变量（设计红线，不得违反）：审批对象确定性、无配额复用、超时非否决、可审计配对（含 `supersedes` 演化链与 `actor` 身份）、与账本轨互不污染。

## 3. 纪律条款（延续 Phase 1，全部有效）

1. 测试基线 **109 passed / 2 skipped 不得回归**；BUILD/VERIFY 分离，verify 阶段不改实现。
2. 内核仓只读：pin `v0.2.0b7` 不动；re-pin 仅经 C1 专项指令。
3. 零 npm 运行时依赖（R2a）持续有效，变更仅可经 §1.5 的 R2b 流程 + owner 确认。
4. 真实 Provider / GPU 调用需 owner 显式授权 + 新 snapshot/binding；Phase 2 全程不涉及。
5. 禁止顺手优化：遇设计不合理处报告并等决策，不自行实现。
6. `bridge.contract.yaml` 任何变更 = 显式 PR + 双仓契约测试 + owner review + 双仓同时 bump `contract_version`。
7. 脱敏纪律延续：ATF 内部路径、业务单据信息、服务器地址不得进入 harness 仓。
