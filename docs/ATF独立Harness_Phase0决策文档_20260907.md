## 决策一：技术栈与结构路线

### 1.1 要决定什么

独立 harness 的 L2（LLM 适配）/ L3（loop + 会话 + 上下文）/ L4（表面形态）用什么技术栈实现、与 Pi/dsh 生态是什么依赖关系。L1（atf CLI、五模块、G1–G7、四事实 Owner）三个选项下都**原样保留、不重写**。

### 1.2 选项对比

| | R1 纯 Python 自建 | **R2 TS harness + Python 内核桥接（推荐主干）** | R3 绑定 dsh 作为 L2–L4 |
|---|---|---|---|
| 结构 | 在 ATF 仓内长出 L2–L3（Python LLM 客户端 + 薄 loop + 会话 log） | L2–L4 用 TS；L1 经 stdio JSONL（Pi RPC 范式）或 ACP 驱动 | ATF 内核写成 dsh 插件（tools + approval + skills provider），经 Cordis + profile 分发 |
| 优势 | 单栈、无桥接、零跨进程调试；团队现有技能 | 复用两个项目最成熟的部分；skills 生态 TS 侧最厚；桥接范式有现成先例（Pi `--mode rpc`） | 白得 approval / questions / sandbox / subagent / web 全家桶 |
| 风险/成本 | pi-ai 用 178 个文件才做到的多 provider 归一需自研，长期成本最高 | 双栈工程复杂度、版本同步、跨进程调试 | **dsh 是 developer preview 且官方明示 breaking changes**；Cordis 深度耦合；训练闸门 sha 语义需深度适配其 approval seam |
| 对闸门语义的影响 | 无影响（自有） | 无影响（L1 自有，闸门在桥接边界之内） | 需把 ApprovalRecord/v1（sha 绑定 + 一次性消费）映射进 dsh approval seam——映射层是最大不确定点 |
| 退出成本 | 低 | 低（桥接边界清晰，L3 可换） | **高**（Cordis 渗透到插件代码内部） |

### 1.3 R2 的内部子选项（依赖深度）

| | R2a 仅借鉴设计，全部自建 TS | R2b 依赖 pi-ai（npm 包） | R2c vendor pi-mono 子集进仓 |
|---|---|---|---|
| 含义 | 参照 Pi 的分层/Result 类型/双管道设计，代码自己写 | 直接 `npm i @earendil-works/pi-ai` 用它的多 provider 层 | 把 pi-ai（或 + agent-core）源码拷入本仓，按 reviewed code 管理 |
| 优势 | 零外部运行时依赖，完全可控 | L2 最难的部分直接白得 | 白得 + 不受上游发布节奏影响，供应链可审计 |
| 风险 | L2 自研工作量回来了 | 上游 breaking 变更风险；商业化项目（Earendil）license/节奏不可控 | 需长期跟上游合并安全补丁，仓体积增大 |
| 适合 | Phase 1 冒烟（单 provider 就够） | Phase 2+ 多 provider 时再评估 | 同 R2b，但更保守 |

### 1.4 推荐

**R2 为主干，起步走 R2a（仅借鉴设计），Phase 2 多 provider 需求出现时再评估升级 R2b/R2c。**理由：

1. 训练闸门必须确定性 fails-closed 且 sha 绑定——Pi 内核哲学不容纳它（闸门是概率性扩展），dsh 的 seam 需要深度适配且版本不稳；
2. R2a 把不可控依赖压缩到"借鉴设计而非绑定运行时"，Phase 1 只需单 provider（OpenAI 兼容即可驱动 vLLM/DeepSeek 端点），自研成本可控；
3. ATF 的 AgentHostTransportConfig/v1 + dispatch/resume 已自带 ACP 式语义，桥接层演化路径短。

**拍板本决策时需连带确认**：R2 下 L3/L4 仓库位置——建议独立新仓（如 `atf-harness/`），与 ATF 内核仓解耦，仅通过 stdio/ACP 合同耦合（与 TEM 独立仓同理）。

## 决策二：会话事实与领域事实的关系

### 2.1 要决定什么

独立形态下必然并存两层日志：**会话 log**（对话/工具调用/决策叙述，harness 层）与 **run journal**（领域 typed facts，四事实 Owner 层）。二者的关系是什么。这是三个决策里**返工代价最大**的：它决定会话事件的 schema 字段，改版意味着历史会话迁移。

### 2.2 选项对比

| | **A. 双层引用（推荐）** | B. 合并单层 | C. 双向引用 |
|---|---|---|---|
| 结构 | 会话事件可携带 `domain_refs: [{journal, digest}]` 指向领域层事实的指纹；领域层**不**回引会话 | 领域事实直接作为会话事件类型写入 session log，一套日志 | 会话 ↔ 领域互存对方 id，可互查 |
| 优点 | 会话可 compaction / 分支 / 丢弃，证据链永远在领域层完整无缺；职责与四 Owner 语义零冲突 | 只有一套日志，实现最简单 | 审计时可从任一侧出发 |
| 缺点 | 引用完整性需要自校验（digest 对不上 = fail-closed block） | **领域事实被卷进会话生命周期**：compaction 可能压掉证据叙述、会话分支导致事实分叉——直接违反 append-only/CAS 语义 | 双向引用形成环，GC 与一致性维护复杂；领域层被迫知道会话层，四 Owner 边界被打破 |
| 与既有原则的关系 | 与"会话层 ≠ 领域层"（教学文档 §5.2）一致 | 与四 Owner append-only 原则**冲突** | 边界模糊 |

### 2.3 推荐：A（双层引用），附三条落地细则

1. **digest 是唯一合法引用形态**：会话事件引用领域事实只允许 `{journal_type, fact_id, sha256_digest}` 三元组，不含事实内容副本；校验失败按缺证据处理 → block（fail-closed，与现有"缺证据/hash 冲突返回 block"原则同构）。
2. **compaction 白名单**：携带 `domain_refs` 的会话事件在 compaction 中只允许摘要叙述、**不允许丢弃引用字段**；无引用的纯叙述事件可自由压缩。
3. **预留 TEM 投影字段**：会话事件 schema 预留 `projection: {evidence_event: candidate_id | null}` 可选字段（Phase 3 回灌时启用）。现在只定字段位，不实现——成本几乎为零，避免 Phase 3 再改 schema。

### 2.4 拍板本决策即产出的东西

会话事件 schema v0 草案（事件类型枚举 + `domain_refs` / `projection` 字段定义），作为 ADR-06 附录，Phase 1 任务书直接引用。

## 决策三：headless 模式的审批语义

### 3.1 要决定什么

无人值守（headless / 宿主子代理）运行时，G1–G7 闸门的审批从哪来。交互壳（TUI/Web）的实时问答不在本决策范围内——那是 UI 面，语义跟随本决策。

### 3.2 选项对比

| | A. 账本单轨（ATF 现状） | B. 自动应答单轨（dsh 式委托信任） | **C. 双轨（推荐）** |
|---|---|---|---|
| 机制 | 审批只能来自预录的 ApprovalRecord/v1（sha 绑定 + 一次性消费）；无预录 → exit 78 | 按配置声明"该子代理在该范围内无需问人"，权限提示自动应答 | 交互壳走实时问答；headless 走账本预录；**两种来源最终都必须落成 ApprovalRecord/v1 才生效** |
| 优点 | 机械强制最强，与现有 exit 78 语义零改动 | 全自动，宿主嵌入体验最好 | 交互体验与无人值守都成立；审批事实仍归四 Owner 单一来源 |
| 缺点 | 交互壳下每次审批都要预先录账本，体验差 | **信任边界靠配置声明，闸门 sha 绑定语义被架空**——zcode 闸门自签教训的重演风险 | 多一条"实时问答 → 落账本"的写入路径要实现 |
| 失败模式 | fail-closed ✅ | fail-open 风险（配置错 = 静默放行） | fail-closed ✅（两轨都以账本记录为准，无记录即拒绝） |

### 3.3 推荐：C（双轨），铁律一条

**实时问答产生的审批必须以 ApprovalRecord/v1 落入 approval ledger 后才允许执行——问答 UI 只是账本的录入前端，不是并行的第二真相源。**这样 dsh 的 user-approval / user-questions 交互面可以直接借鉴，而闸门的确定性 fails-closed + sha 绑定语义完整保留在 L1，不被任何 harness 层削弱。

连带细则：headless 下 exit code 语义沿用现状（78 = 无审批失败退出，0 = 成功，其他非零 = 各类 block），Phase 1 任务书给出完整 exit code 表。

## 决策四：灵活创作层——训练大脑的自由编写空间

### 4.1 要决定什么

ATF 独立化为"训练大脑"后，agent 需要根据训练情况、训练任务、用户指令**灵活编写代码和文件**（badcase 归因脚本、数据探查、实验草稿、新分析工具）。问题：这个自由度在哪里实现、产物怎么管理、如何不污染事实链。当前 ATF 的自我感知是"不够灵活"——根因是 **v0.x 把探索性动作和执行性动作放在同一平面，全都直接站在闸门口付同样的治理成本；缺的是闸门上游的"假设容器"**，而不是闸门太严。

核心设计哲学（贯穿四个决策的总纲）：**生成自由、生效收敛**——大模型负责生成假设（代码/文件/计划/建议），确定性工程负责裁决哪些假设能触碰现实。

### 4.2 选项对比

| | **A. 三层工作区 + 晋升闸（推荐）** | B. 维持现状单平面 | C. 轻量两级 |
|---|---|---|---|
| 结构 | T0 自由创作区（scratch，零闸门）→ 晋升闸 A → T1 受控 Artifact 区（immutable）→ 晋升闸 B → T2 冻结合同区 | 所有动作统一过闸门，无独立自由区 | T0 自由区 + T2 合同区，中间产物直接进现有 Artifact Catalog（闸门即为唯一晋升路径） |
| 灵活度 | 探索成本趋近零，大脑"敢想" | 探索成本 = 治理成本，agent 不敢写（现状痛点） | 与 A 的 T0 相同，但 T1 的准入粒度粗 |
| 治理强度 | 晋升闸 A：可复现 + 幂等 + sha；晋升闸 B：决策记录 + 审批 | 最强但一刀切 | 闸门语义与现状完全一致 |
| 成本 | 新增晋升闸 A 校验器 + scratch provenance 元数据 | 零（但也解决不了问题） | 最小增量 |
| 风险 | T0 边界若不清晰会变成"第二事实源"——需铁律约束（见 4.4） | 独立化后灵活性诉求必然撞墙 | 归因脚本/草稿类产物要么进不了证据链、要么被迫全量过闸 |

### 4.3 四类灵活产出分别挂哪层

| agent 想灵活做的事 | 归属层 | 说明 |
|---|---|---|
| 写分析/检查代码（badcase 归因、数据探查） | T0 随便写 | 探索成本必须趋近零 |
| 起草下一轮实验计划 | T0 → 产出 `Suggestion` | 现有"单一 atomic change group + prior-best baseline"机制天然承接——模型自由度前移到建议端，决策端是人 |
| 数据/指标/归因结论需要被后续引用 | 必须过晋升闸 A 升 T1 | 引用即证据，证据必须不可变 |
| 修改合同/prompt/字段定义 | 过晋升闸 B 升 T2 | 走 Decision Ledger，最高门槛 |

### 4.4 推荐：A（三层工作区 + 晋升闸），附四条细则

1. **铁律一（引用规则）**：T0 可以被阅读，**不可被引用为证据**——任何进入 run journal 的事实只能指向 T1+ 的 Artifact。这一条把"灵活"与"可信"彻底解耦：agent 写一万行脚本都不污染事实链，同时堵死 T0 变成"第二事实源"的路径。
2. **铁律二（TCB 边界）**：agent 编写的代码永远在可信计算基（TCB）之外——执行时沙箱 workspace-write 档、run 数据只读、**无权调用闸门签署工具**。这正是 Pi 的自扩展（`/reload` 热加载让 agent 代码进 TCB）不能照搬的原因：zcode 闸门自签教训已证明训练场景不行。
3. **provenance 元数据**：T0 产物带四元组（所属 run、触发指令、生成模型版本、时间戳）；scratch 生命周期为 run 级，run 关闭后归档可清理。
4. **资产复用**：workspace 合同扩展出 `scratch/` 子目录（T0）；Artifact Catalog 原样做 T1；Decision Ledger 原样做 T2。**唯一新增实现 = 晋升闸 A 校验器**（可复现 + 幂等 + sha 指纹）。

### 4.5 拍板本决策即产出的东西

workspace 目录结构 v0（`scratch/` / `artifacts/` / `contracts/` 三层定义）+ 引用规则条款 + TCB 边界声明，作为 ADR-08 附录，Phase 1 任务书直接引用（冒烟范围即含一次"T0 分析脚本 → 晋升闸 A → T1 Artifact"的演示路径）。

## 5. 决策间的依赖关系

```text
决策一（R2a）──→ 决定 Phase 1 用什么语言/仓骨架写 L2-L3
决策二（A）───→ 决定会话事件 schema（Phase 1 落盘格式直接引用）
决策三（C）───→ 决定审批调用方接口（Phase 1 审批走账本轨）
决策四（A）───→ 决定 workspace 目录结构与引用规则（scratch/ 与晋升闸 A 进入冒烟范围）
四者在 Phase 1 任务书中汇合为：TS 薄 harness（单 provider + 薄 loop + 双层会话 schema）
+ stdio JSONL 驱动 atf CLI + 审批走账本 + 三层工作区
→ Faux provider 冒烟「数据准入→G2」（含一次 T0→晋升闸 A→T1 的演示路径）
```

若你对决策一的拍板不是 R2（例如选 R1 纯 Python），决策二/三/四的结论不受影响，仅 Phase 1 任务书的技术措辞需相应调整。决策四与决策二存在一处交叉：T0"不可被引用为证据"（铁律一）正是 `domain_refs` 只认 T1+ Artifact 的引用规则在事实侧的镜像——两条建议同拍同改。
