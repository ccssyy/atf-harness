# ATF 决策理由档案（为什么这么定）

> 配套：[ATF_项目纠正总纲_20261120.md](ATF_项目纠正总纲_20261120.md) §四 决策记录、[ATF_重装重构方案_20261120.md](ATF_重装重构方案_20261120.md)
> 用途：交接件只装结论，**推理链条放这里**。遇到「为什么不留 / 为什么要删」时读本文，不要凭结论反推理由。

---

## D1：重构路线选「基于干净 vendor 重装」

**结论**：不做渐进替换，一次性把 12,745 行重复清掉，把领域资产重新适配到 vendor 原生接口。

**推理链**：

1. 先算了依赖纠缠度（实测 grep）：
   ```
   atf-tools → src/ 的 74 处依赖
     ├── core/workspace（训练域·保留）  57 处
     ├── webui/（重复·要删）             9 处
     ├── agent/file（重复·要删）          4 处
     └── core/tools（部分重复）           4 处
   → 只有 13 处依赖真正要删的模块
   ```
   **如果纠缠是 50 处，渐进替换必然；13 处则重装成本可控。**

2. 再算测试资产：
   ```
   241 个测试文件
     ├── 74 个纯黑盒（只依赖 packages/）→ 重装后直接跑通
     └── 约 155 个白盒（依赖 src/）    → 随模块删，不算损失
   ```
   **白盒测试跟着模块一起删，不是浪费。**

3. 最后算审计器价值：三层审计器给了「施工图 + 验收标准」，**没有它重装就是瞎删**。

**被否决的替代方案**：
- 渐进替换（B 批次逐个清）→ 中间态多，容易「修一半又回旧路径」
- 全部重写 → 会丢 37% 领域资产 + 155 个测试锚

**风险已认**：5-7 周，中间产品不可用（靠 dev 跑旧代码缓解）。

## D2：MCP 与重装合并做

**结论**：不分成两轮，重装时直接按 MCP 形态搭。

**推理链**：

1. 重装本身要让内核接口动一次（因为要删 bridge）
2. 如果先重装（保留 bridge）再 MCP 化（删 bridge），**内核要改两次**
3. 合并做只改一次，省一整轮返工

**代价**：Phase 1（内核 MCP）必须与 Phase 0 并行，增加协调复杂度。

## D3：patch 8→6 + 2 插件（关键分类）

**结论**：

| patch | 判定 | 理由 |
|---|---|---|
| 0002 composer-placeholder | **改插件** | DSH 有 `ctx.locale.register(NS, {zh,en})`（实证：`ui-jobs/index.ts:34` 就是范例） |
| 0004 api-key-reveal | **改插件** | `ui-settings-models/src/client/slot-contract.ts` 明写「a plugin distributed **outside this repository** adds UI to the Models settings section **without editing it**」 |
| 0003 form-intent | **保留** | `user-questions/types.ts:18-22` 明写「**Tagged so further intents can be added**」——这是上游设计的开放扩展点，ATF 补 `form` 是「按设计意图填坑」，不是 Fork |
| 0005 form-cancel | **保留** | 随 0003 |
| 0001 fixed-launch-token | **保留** | `browser-auth.ts` 内部逻辑，无插件点；且该 env 是 patch 引入的（实测 grep `^\+.*LAUNCH_TOKEN`） |
| 0006 settings-host-persistence | **保留** | `persistence: 'host' \| 'memory'` 硬编码在组件构造里，无配置面 |
| 0007 workspace-picker-root | **保留** | host 侧目录选择器，无插件点；env 也是 patch 引入的 |
| 0008 bash-env-passthrough | **保留** | shell 服务内部，无插件点 |

**推理要点**：
- **不能一律归零**——owner 指出「patch 有些是 ATF 特定新增的 UI 或配置项」
- **判据是「有没有插件扩展点」**，不是「patch 数量越少越好」
- 0003/0005 是**正当扩展**（上游留了口子），不该算技术债

**被否决**：
- 「8 → 2」（只留 form 系列）→ 错，0001/0006/0007/0008 无插件点
- 「提 PR 给上游」→ owner 裁定：独立产品，不建连接

## D4：不向上游提 PR

**结论**：vendor 独立维护，升级时拉取同步再重放 patch。

**owner 原话**：「vendor 不用跟上游建立连接，不要给上游pr，这是个独立产品，如果以后要升级vendor也只拉取同步再重新适配patch和插件」

**推论**：
- patch 数量本身不是问题（是独立产品的必然成本）
- **真问题是「同步流程没机检」** → Phase 0-4 要做 vendor 同步检查器
- 目标从「减少 patch」改为「patch/插件边界清晰 + 同步可验证」

## D5：dev 全程保持可用

**结论**：新代码在 worktree 搭到可用再切，dev 跑旧代码。

**推理**：用户拒绝 5-7 周不可用。且今天已有 worktree 实践（`proj-correction`），模式成熟。

**具体做法**：Phase 0-4 全在 worktree，Phase 5 才切 dev。

## D6：MCP 工具名加适配层（不用 `mcp__atf__*`）

**结论**：`atf-tools` 加薄适配，模型可见名保持 `atf_*`。

**推理链**：

1. MCP 原生命名是 `mcp__<serverName>__<rawName>`（实证 `mcp-client/src/tools.ts:7-8`）
2. 若接受改名，破坏面：
   - 所有测试断言里的工具名
   - `APPROVAL_SEMANTICS_BY_TOOL` 映射表（`toolDefinition.ts`）
   - persona / 工具描述引用
   - 用户可见回执
3. 适配层成本约 100 行，换零破坏

**代价**：多一层间接（`atf_*` → `mcp__atf__*`），但可测。

## D7：内核 MCP 手写最小实现（不用官方 SDK）

**结论**：手写 JSON-RPC 2.0 over stdio，约 200 行，零新依赖。

**推理链**：

1. 内核仓当前依赖只有 `Pillow` + `numpy`（低依赖纪律）
2. 加 MCP SDK 会破坏该纪律；且 A800 容器 site-packages 已有 stale 问题
3. **MCP over stdio 本质是 JSON-RPC 2.0 + 行分帧**，协议不复杂
4. 手写可控，且能复用内核现有的 `session/frames.py` 分帧经验

**风险**：手写可能有协议偏差 → **缓解：先写 15 个方法的契约测试，再实现**（测试驱动）。

## D9：pin 树承认退役

**结论**：不删 pin 树目录，但明确它不再作为加载源。

**推理链（实测 `dev.env`）**：
```
ATF_INSTANCE_PIN_ROOT='/data/atf/dev/pinned'      ← pin 树
ATF_KERNEL_SOURCE='/data/sam/AgenticTrainingFlow'  ← 实际加载源（主仓 main）
ATF_DSH_KERNEL_DIR="$ATF_KERNEL_SOURCE"            ← 从这加载
ATF_DSH_PIPELINE_COMMAND="...$ATF_KERNEL_SOURCE/..." ← 从这加载
ATF_DSH_BRIDGE_COMMAND="PYTHONPATH=$ATF_KERNEL_SOURCE/src ..."  ← 从这加载
```

**pin 树现在只做两件事**：
1. `resolveInstancePinRoot()` 返回它（boot preflight 校验用）
2. 被加进 `ATF_V1_FILE_TOOL_ROOTS` 文件白名单

**真实用途只剩「白名单根」**——如果不让 agent 读 pin 树，它就彻底没用了。

**需要随之清理的 5 个文件**（实测 grep）：
```
src/agent/main.ts            ← 要删（B2）
src/agent/cli.ts             ← 要删（B2）
src/core/workspace/bootPreflight.ts ← 要删（B 类）
src/core/workspace/instancePin.ts   ← 直接删
src/webui/server.ts          ← 要删（B7）
```

**推论**：pin 退役**随重装自然完成**，不需要单独一批——因为 4/5 个文件本来就要删。

## D10：`atf_pipeline_stage` 不 MCP 化

**结论**：保持直接 spawn CLI。

**推理链（实测）**：

1. 39 个 harness 工具的构成：
   ```
   桥接面（走 bridge）     约 16 个
   训练域本地工具          约 13 个（读 run 目录/GPU/tmux）
   确认卡工具               2 个
   子任务派发               4 个
   提示/自检                1 个
   atf_pipeline_stage       1 个 ← 特殊
   ```
2. `atf_pipeline_stage` **不走 bridge**，直接 spawn `walkthrough_pipeline.py`（`ATF_DSH_PIPELINE_COMMAND`）
3. 段脚本是**确定性 CLI**（`--stage X` 跑完退出），MCP 包裹无收益

**重要推论**：**MCP 化只覆盖 15 个内核方法，不是 39 个工具**。这必须在方案里如实披露，否则会高估收益。
