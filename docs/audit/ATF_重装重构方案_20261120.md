## 一、为什么选重装而不是渐进替换

### 决策依据（实测数据）

| 指标 | 实测值 | 含义 |
|---|---|---|
| `atf-tools` → **要删的重复模块** 依赖 | **13 处** | 脱钩成本极低 |
| `atf-tools` → 领域保留模块 依赖 | 57 处 | 领域资产自然保留 |
| 黑盒测试（只依赖 packages/） | 74 个 | **重装后直接跑通，不用重写** |
| 白盒测试（依赖 src/ 旧实现） | 约 155 个 | 随模块删除而删，不算损失 |
| 三层审计器 | 已就绪 | **提供施工图 + 验收标准** |

### 三条硬理由

1. **依赖纠缠只有 13 处**——改完这 13 处，`atf-tools` 就完全脱离重复模块。渐进替换反而要经历「两套并存」的中间期，更容易乱。
2. **审计器给了安全网**——`npm run audit:all` 可随时验证「重复是否清零」，白名单只减不增。这是渐进替换给不了的。
3. **白盒测试跟着模块删，不是损失**——模块没了，测它内部逻辑也没意义。

### 与文章参考的呼应

参考文章（「用 DSH 做 AIOps 平台」）的核心警告：

> 「很多团队做类似平台，最后都变成一个自己维护的 Agent 框架——推理链路、上下文管理、工具调度全部自研。半年后引擎厂商升级一次，就要跟着重写一次。」

**ATF 已经走到这一步**（自研 loop 5,218 行 + LLM 2,615 行 + compaction 1,538 行）。重装是把这个方向掰回来。

## 四、Patch 裁定（owner 已定）

| patch | 内容 | 裁定 |
|---|---|---|
| 0002 composer-placeholder | locale 文案 | **保留**（实测：`locale.register` 是单占位，重复注册抛错——见下方修正记录） |
| 0004 api-key-reveal | Models 卡 UI | **保留**（实测：`provider-card` slot 只给 `provider/configured/keyConfigured`，拿不到组件内部 `keyDraft`） |
| 0001 fixed-launch-token | `DSH_WEB_LAUNCH_TOKEN` env | **保留**（无插件点） |
| 0003 form-intent | 表单卡 intent | **保留**（依上游 intent 扩展点设计，正当扩展） |
| 0005 form-cancel | 表单卡取消 | **保留**（随 0003） |
| 0006 settings-host-persistence | 设置持久化 | **保留**（无配置面） |
| 0007 workspace-picker-root | 选择器根 | **保留**（无插件点） |
| 0008 bash-env-passthrough | env 透传 | **保留**（无插件点） |

**修正后的目标：8 → 8 patch，0 新增插件。**

**实测发现（2026-11-20 G0 实施中）：vendor 的扩展模型是「只允许追加，不允许覆盖」**——
- `locale.register(ns, locale, dict)` 对已存在的 (ns, locale) **直接抛错**（`already has locale`）
- `provider-card` slot 是「扩展区域」，props 只有只读的目录行信息，**无法替换组件内部的状态与渲染**

因此凡是「**改已有行为**」的诉求，插件做不到，只能 patch。这不是技术债，是 vendor 扩展点的设计边界。

**推论（对未来有指导意义）**：

| 诉求 | 能否插件 |
|---|---|
| 加新能力（新 namespace / 新 slot / 新工具） | ✅ 可以 |
| 改已有行为（覆盖文案 / 改组件内部） | ❌ 必须 patch |

**不做**：不向上游提 PR（owner 裁定：独立产品，升级时拉取同步再重放）。

## 五、MCP 化（与重装合并做，owner 已裁）

**理由**：重装时内核接口本来就要动，MCP 化一起做只改一次；分开做要改两次。

### 目标形态

```
harness → ctx.mcp（vendor mcp-client，stdio）→ atf_mcp_server.py → 15 个内核方法
```

### 关键决策（已定）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 工具改名 | **加薄适配层**，模型可见名保持 `atf_*`（不用 `mcp__atf__*`） |
| 2 | 内核实现 | **手写最小 MCP stdio 实现**（约 200 行，零新依赖，保内核低依赖纪律） |
| 3 | `atf_pipeline_stage` | **不 MCP 化**（确定性 CLI，直接 spawn，MCP 包裹无收益） |

### 收益

- 删 `src/bridge/` 1,143 行 + 内核分帧层约 600 行
- 消除 `bridge.contract.yaml` 第三份协议声明
- 消除 `contract_version` 与 pin 的双轴演进
- **获得 vendor 治理面**：spill / pruner / timeout 对桥接工具自动生效（当前绕开）
- 获得原生重连与工具调用超时

### 魔鬼代言人（反例）

**反例 1：这不是「重装」，是「边跑边换发动机」**
- 触发：Phase 2 删 `src/agent` 时，`atf-subagent` 还没改完
- 影响：子任务派发断
- 缓解：**严格按 2-5 → 2-6 顺序**，先接新路径再删旧

**反例 2：MCP 化让内核成为「第二个要维护的协议」**
- 触发：手写 MCP 实现有偏差
- 影响：不如现有 bridge 稳
- 缓解：**手写前先写 15 个方法的契约测试**，用测试驱动实现

**反例 3：5-7 周后产品还是不可用**
- 触发：Phase 缺陷累积
- 影响：投入打水漂
- 缓解：**Phase 0-1 各出一个可交付物**（locale 插件、MCP server），中途可评估
