### 1.2 zcode 的总结是高质量的，但存在一个盲区

`验证轮问题盘点与收敛路径_20261119.md` 的 A/B/C 对象三分方法是**正确且专业**的——它解决了"登记混装一包=逐个修永远修不完"的感受来源。C 类（判据面缺口）的自诊断尤其准确：

这个诊断是对的。但它**止步于"行为面测不出来"**，没有追问：为什么 agent 的行为会跑偏到那些地方？

### 1.3 我的审计补上了这一层：三个 zcode 分类中不存在的根因

| 我的发现 | zcode 分类中的位置 | 说明 |
|---|---|---|
| **分组确认闸校验错对象**（读顶层 `confirmed` 而非 `grouping.confirmed`，已真实内核复现） | ❌ **不存在** | 这是 B1「agent 跳段」的上游原因之一：闸根本没在判它宣称的东西 |
| **用户分组凭据 per-doc 写 / run 级读**（多类 run 确认事实 100% 丢失） | ❌ **不存在** | 这是 B2「确认后又弹」的上游原因之一：内核读不到用户的确认 |
| **段序双判据**（`missing_prereqs` 全仓零调用，实跑的是另一张手写键表） | ❌ **不存在** | 这是 B1「跳段」的结构化成因 |

**关键证据**：`_gate_confirmed_for` 在全部文档里只出现两次，且**两次都是"把它从 A 挪到 B"的迁移记录**：

```
docs/decisions/0020-granularity-unification-single-stage-order.md:88
docs/architecture/g-batch-and-schema-master-plan.md:33
```

**从来没有人检查过它判定的是什么。** 这就是它能活下来的原因——它长得像闸、叫着闸的名字、还在正确的调用位置，唯独判的对象是错的。

### 1.4 这意味着什么

zcode 的 A/B/C 是**按症状分类**（跳段、弹卡循环、卡面标识）。我的发现是**按机制分类**（闸判错对象、凭据断链、判据双源）。

两种分类**不冲突，而是层次不同**：

```
症状层（zcode A/B/C）     B1 跳段 / B2 pending 循环 / B3 卡面标识
                                ↑ 由什么产生？
机制层（本方案）          分组闸判错对象 / 凭据断链 / 段序双判据
                                ↑ 由什么产生？
架构层                    流程控制权未落地 + 三套执行线只跑一套
```

**只修症状层 → 下一轮换个形状再撞**（这正是过去三轮的模式：1110 P1-P6 → 1112 M1-M8 → 1119 七项）。
**只修机制层 → 症状不一定全消**（因为还有纯行为面问题）。
**两层一起修 + 补判据面 → 才能收敛。**

## 二、接手方案：三层并行，以判据先行

### 核心原则

zcode 文档自己写了正确的一句话：

> **C1 faux 断言随 B 类批同步写（判据先行）**

我完全同意，并建议把它提升为全局纪律：**每个修复必须先有能变红的测试，再动代码。**

理由：`_gate_confirmed_for` 的案例证明，没有测试的闸可以错很久而无人知——它零测试覆盖。

### 第 0 层：判据基建（先做，1-2 天，不修任何 bug）

这是**最高杠杆**的一步。zcode 的 C1 已经指出方向，但缺具体落法。

| 编号 | 事项 | 判据 | 为什么必须先行 |
|---|---|---|---|
| **0-1** | 段序一致性断言：`stage_registry.prereq_stages` 与 `_STAGE_CTX_KEYS` 的差异**显式化为测试** | 任一差异被测试点名，而非静默共存 | 不先做这个，改 A 类时无法判断"改对了还是改坏了" |
| **0-2** | 闸门判定对象断言：每个 `_gate_*`/`_xxx_done_for` 函数必须有测试证明它**在判它宣称的东西** | 构造"闸应拦"与"闸应放"两态 | 直接防 `_gate_confirmed_for` 这类缺陷复发 |
| **0-3** | **LLM 旅程回归**（zcode C1） | faux 脚本断言（确定性进 CI）+ 真 LLM headless 冒烟 | 覆盖 7 项缺陷所在的真实失效面 |
| **0-4** | 收敛度量（zcode C2） | 每轮缺陷数按 A/B/C + **机制层**四分类计数入台账 | 无趋势线=无法判断是否真在收敛 |

**0-1 和 0-2 是我加的**——zcode 的 C 类没有这两条，但它们成本极低、收益最高。

### 第 1 层：机制修复（判据就绪后立即做）

按"改动面小、危害大、可验证"排序：

| 编号 | 缺陷 | 改动面（实测） | 测试现状 | 风险 | 验收 |
|---|---|---|---|---|---|
| **1-1** | 分组闸判错对象 | 1 函数 + 2 调用点 | **零覆盖** | 低（旧 run 兼容已验） | 场景 A 翻转 + B/C/D 零回归 |
| **1-2** | per-doc 凭据失配 | 内核读侧 1 处 | 需新增 | 中低（需兼容单类） | 多类 run 卡上选定→内核读到 |
| **1-3** | `_STAGE_MAP` 陈旧 | 2 行（调整构建顺序） | 无消费者 | 极低 | 实机断言 `stage_entry_of().param_requirements` 非空 |
| **1-4** | 会话路径自我嵌套 | 1 处 `absolutePath` | 需新增 | 低 | 新会话目录不再套娃 |

**1-1 的修复逻辑我已做等价验证**（真实内核复现 + 四场景对照表），可立即实施。

### 第 2 层：架构决策（需你拍板，不由我单方面定）

| 编号 | 决策点 | 现状 | 三选一 |
|---|---|---|---|
| **2-1** | **三套执行线去留** | 甲线/丙线占 10.6k 行，dev **未装配**；文档称"两线一内核" | (a) 废弃删除，减认知负担<br>(b) 保留给 TUI/CLI/ACP，文档明确"WebUI 与 TUI 行为不同"<br>(c) 统一到 DSH 面，甲丙线只留测试价值 |
| **2-2** | **段序单源化** | 两套判据并存，声明侧全死 | (a) 让 `missing_prereqs` 真正生效，删 `_STAGE_CTX_KEYS`<br>(b) 反向：删 `prereq_stages` 声明，承认产物依赖是唯一真相<br>(c) 保持双源，但加 0-1 一致性测试 |
| **2-3** | **卡面独立性**（zcode B 类的本质） | 卡面依附工具执行，绕行即失守 | (a) 卡面改为流程一等公民（独立于工具执行）<br>(b) 保留依附，但堵死绕行通道<br>(c) 接受绕行，靠审计兜底 |

**我的建议**：2-1 选 (b)（成本最低、诚实）、2-2 选 (a)（符合 1115 已裁的"驱动权归一"方向）、2-3 选 (a) 但分阶段。

**理由**：2-1(b) 让文档说的和实际跑的一致，不需要删代码也不用假装两线都在跑。2-2(a) 是 1115 owner 终裁的原意——那次裁定了方向但只执行了"删旧 driver"那一半，"建新 driver"没落地。2-3(a) 是唯一能真正兑现"用户决定权"的路径，但成本最高，可先做 1-1/1-2 缓解。

### 第 3 层：zcode 的 A/B/C 批（在其判据就绪后执行）

这些**已有清晰方案**，我接手执行即可：

- **A 类 4 项**：护栏/硬阻塞，TDD 可闭
- **B 类 3 项**：编排语义重设计（zcode 建议 B 类先行，我同意——它同时消掉两个最痛体验）
- **C 类 2 项**：已并入第 0 层

## 三、执行顺序（建议）

```
第 0 层（判据基建）            ← 高杠杆，1-2 天
  ├─ 0-2 闸门判定对象断言      ← 最优先，直接防复发
  ├─ 0-1 段序一致性断言
  └─ 0-3/0-4 LLM 回归 + 度量

第 1 层（机制修复）            ← 判据就绪后立即
  ├─ 1-1 分组闸（最高优先）
  ├─ 1-3 _STAGE_MAP
  ├─ 1-4 会话路径
  └─ 1-2 per-doc 凭据

第 2 层（架构决策）            ← 需你拍板
  └─ 2-1 / 2-2 / 2-3

第 3 层（zcode A/B/C 批）      ← 按 zcode 优先级执行
```

**为什么第 0 层先行**：如果先修 1-1，没有测试锁定，下一个开发者可能再次把判定改回顶层 `confirmed`（或新增另一个闸时踩同样的坑）。**0-2 是防止这类缺陷复发的唯一手段。**

## 五、对"为什么不碰训练评估面"的重新回答

你问到点上了。我原答案错了，正确回答是：

**应该碰，而且必须碰。**

理由：
1. **零 GPU 可验证**：`tests/adapters/` 117 passed / 3.46s 已实测
2. **它是产品价值闭环的终点**：17 段流程最后 4 段（`training_prep`→`training_run`→`checkpoint_eval`→`badcase_analysis`）全在这里
3. **它有独立缺陷面**：`atf_run_training` 涉及 GPU 排队窗口、danger 卡、tmux 双启闸、启动探活——任何一环错都是产品级故障（zcode 记录过 `cr_r2` 三连败实锚）

**我先前不碰的真实原因**是不对的：那是"没读就下结论"的偷懒，不是"需 GPU"的正当理由。

**现在补充的实测结论**（本轮新读）：

| 面 | 关键实现 | 风险点 |
|---|---|---|
| 训练启动 | `atf_run_training` → GPU 排队窗口 → danger 卡 → `execSync(tmux new-session ...)` → 启动探活 | 有完整防线：端口预检、双启串行闸、终止特征检测、exit.code 捕获 |
| 训练控制面 | `control_plane.py` 2625 行，`LocalSubprocessExecutor` + `Popen.poll` 轮询 | 结构化良好（typed receipt / integrity_digest） |
| 评估服务 | `vllm_service.py` 1532 行，`start`/`stop_group`/health 轮询 | 有服务健康与 base/LoRA 分别检查，不把 health 成功误报为业务成功 |
