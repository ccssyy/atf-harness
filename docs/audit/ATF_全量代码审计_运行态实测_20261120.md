## 摘要

ATF 是一个已完成度相当高的垂域训练 Agent 产品：内核的确定性校验、事实账本、183 码错误改法目录、六步部署门禁均为真资产且工作正常。但产品主线在真机上"不能像 Agent 那样顺畅运行"，根因不在 bug 密度，而在**三个结构性事实**：

1. **运行态与文档叙述不一致**：dev 实际装配的是 DSH vendor AgentLoop + `atf-tools` 扩展；harness 自研的甲线（`src/core/run`，37k 行）与丙线（`src/agent`）**未装配**。团队大量治理投入落在不在运行的代码上。
2. **流程控制权未落地**：17 段的段序在 `stage_registry` 有完整声明，但唯一的执行判定函数 `missing_prereqs()` **全仓零调用零测试**；真正在跑的是另一张手写键表 `_STAGE_CTX_KEYS`。两套判据互不引用。
3. **用户确认可被静默绕过**：分组确认闸读的是实验配置顶层的 `confirmed` 块，而该块由构建脚本**无条件写入**。已用真实内核复现：分组未确认时闸仍放行切分。

本报告对每个结论给出**文件:行号**与**复现实验**双重证据，并诚实标注了审计过程中被推翻的初判。

### 1.3 运行时缺陷：会话存储路径自我嵌套

实测 151 个会话目录全部呈如下形态（路径长 264 字符）：

```
/data/sam/ATF-Harness/tmp/webui-sessions-dev/data/sam/ATF-Harness/tmp/webui-sessions-dev/
  --data-sam-ATF-Harness-tmp-webui-sessions-dev-...-dispatch-zmT7sU--/xxx.jsonl
```

**根因**（已定位到具体行）：

```ts
// src/webui/sessionManager.ts:483-484
const repo = createJsonlSessionRepo(this.deps.sessionsRoot);
const mirrored = await repo.create({ cwd: this.deps.sessionsRoot }, BACKGROUND_CONTEXT);

// src/agent/sessionMirror.ts:72-74
public async absolutePath(path: string): Promise<Result<string, FileError>> {
  return ok(join(this.cwd, path));     // 绝对路径也被拼到 cwd 后

```

`join()` 对绝对路径并不重置基准，导致 `sessionsRoot` 被当作相对路径二次拼接。**这是实现缺陷，非设计缺陷。**

## 二、缺陷清单（按严重度，均带证据）

### 缺陷 A｜段序：两套判据并存，声明那一侧是死的

**声明源**（`src/agentic_training_flow/application/stage_registry.py`）：17 个 `StageEntry` 均带 `prereq_stages`，docstring 自称"R3 强制的唯一判定源"（`:64`）。

**唯一执行函数**（`:272-280`）：

```python
def missing_prereqs(stage: str, completed: frozenset[str]) -> tuple[str, ...]:
    """链序实查（R3 强制的唯一判定源）。"""
    entry = _STAGE_MAP[stage]
    return tuple(s for s in entry.prereq_stages if s not in completed)
```

**全仓验证**：
```bash
$ grep -rn "missing_prereqs" --include=*.py . | grep -v build/
./src/agentic_training_flow/application/stage_registry.py:272:def missing_prereqs(...)
```
**仅定义行，零调用，零测试。**

**实际执行源**（`skills/atf-admit-training-data/scripts/walkthrough_pipeline.py`）：

```python
# :1448-1459
def _prereq(self, stage: str, *keys: str) -> bool:
    missing = [key for key in keys if key not in self.ctx]     # 只看 ctx 键存在性
```
ctx 键由 `_rehydrate_ctx_for_stage` 按**盘上文件在场性**灌入（`:1523-1600`）。

**两套判据对照**（自动化比对，17 段无一对应）：

| 段 | 声明依赖 | 实际检查 | 一致 |
|---|---|---|---|
| ingest | 段 `contract` | （空） | ❌ |
| register | 段 `inspect` | （空） | ❌ |
| family_split | 段 `experiment_setup` | `split_dir/commit_pin/repository_id`（register 段即产生） | ❌ |
| admission | 段 `publish` | 键 `family_split` | ❌ |

**复现实验（本次实测）**：

| 场景 | 结果 | 判定 |
|---|---|---|
| 空 workspace 直接跑 family_split | `blocked / walkthrough_upstream_not_ok` (exit 2) | 拦得住 |
| register 已跑、跳过 experiment_setup 跑 family_split | `blocked / grouping_gate_pending` (exit 2) | **拦得住** |

> **初判修正**：审计初期判定"跳段可随意发生"。实测证明在 `family_split` 这个具体段上，因内核另有 `grouping_gate_pending` 兜底，跳段被拦住。**缺陷 A 的真实范围是"判据双源且声明侧全死"，而非"跳段畅通无阻"**——某些段被别的闸阴差阳错挡住，另一些段没有。

**残余风险**：某个段如果既无独立业务闸、其 ctx 键又恰好由前序段产物满足，则可被跳过。`contract`/`ingest`/`register` 三段 `_prereq` 为空（`:200-204`），是高风险面。

### 缺陷 B｜分组确认闸校验错对象（已完整复现，最高优先级）

**闸门实现**（`walkthrough_pipeline.py:4195-4209`）：

```python
def _gate_confirmed_for(self, doc_type: str) -> bool:
    """只读判定指定单据类型的实验门是否已带用户确认态(分组闸齐备判定)。"""
    ...
    config = self._read_json_if_file(path)
    return (isinstance(config, dict)
            and isinstance(config.get("confirmed"), dict)
            and bool(config["confirmed"]))     # ← 读顶层 confirmed，不是 grouping.confirmed
```

**该块的写入方**（`build_experiment_setup.py:2483-2487`）**无条件写死**：

```python
cfg["confirmed"] = OrderedDict([
    ("by", "user"), ("at", _now), ("channel", args.confirmation_channel),
])
```

**真实内核复现实验**（本次在 A800 实跑，非推演）：

1. 正常跑 register（rc=0）
2. 手工构造 `experiment-config.json`，使 `grouping.confirmed=False`、顶层 `confirmed` 有值
3. 跑 `family_split`

结果：
```
[场景] grouping.confirmed=0    顶层 confirmed={'by':'user',...}
[结果] family_split rc=0   stages={'family_split':'ok'}   reason_codes=无

结论: 未拦 → 缺陷B成立（分组未确认却放行切分）
```

**同时被证实"完全跳过实验门会被拦"**（`grouping_gate_pending`）——说明闸是存在的、是工作的，**只是判定键选错**。

**连带问题：自证闭环**

```python
# walkthrough_pipeline.py:3696-3700
config["confirmed"] = {"by": "walkthrough-pipeline", "at": _utc_now(), "channel": "script"}
```
而内核 publish 闸只校验 `at` 非空（`src/agentic_training_flow/skills/extraction_data.py:427`）。**驱动自己填的 `by` 满足驱动自己要过的闸**——ADR-0008「用户确认」在这一层退化为「driver 说出了一句话」。

### 缺陷 C｜用户分组意愿三处落盘，主路径必然读不到

**写入侧**（harness，per-doc 形态）：

**读取侧**（内核，run 级形态，硬编码无后缀）：

## 三、为什么"反复开发都不能从根本上修复"

三个正反馈环：

**环 1 · 修描述而非修机制**
每条真机规则沉淀为描述文字 → 描述涨至 4,171 字符 + 45 参数 → agent 更难读懂 → 更多误判 → 更多描述。已实测 6 处自相矛盾。

**环 2 · 双判据漂移**
`stage_registry` 声明 vs `_STAGE_CTX_KEYS` 手写表；per-doc vs run 级凭据；`_completed_stages` 读顶层 `exit_code` vs `_register_done_for` 读 `results[].status`。**修一边，另一边开始漂移。**

**环 3 · 修了不在运行的代码**
团队治理投入大量落在甲线/丙线，而 dev 跑 DSH 面。这是"反复修不好"的**最大单一因素**。
